# Backend Requirements and Design Notes

The backend is starting again from requirements with a developer-created NestJS scaffold in `backend/`. That scaffold is not evidence that the API, identity, persistence or operational requirements below are implemented or verified. The existing frontend remains a Stack Auth starter and likewise does not establish backend behavior.

The developer implements the backend inside `backend/`, alongside `frontend/`. The [backend README](../../backend/README.md) documents current startup, configuration, health behavior and test coverage. Broader requirements below follow in later milestones. Use [engineering conventions](../architecture/BACKEND_CONVENTIONS.md) for responsibility and review rules; explicit tooling requests do not authorize automatically implementing review findings.

Use the [SRS](TenantFlow-SRS.md) for product rules, [schema references](../../schemas.ts) and [enums](../../enum.ts) for the provisional model vocabulary, and [roadmap](../planning/ROADMAP.md) for implementation sequencing. This document preserves backend-specific design knowledge and unresolved decisions from retired tutorials; it does not prescribe a finished architecture.

## 1. Boundaries and identity ownership

- **User direction, updated 23 October 2026:** TenantFlow is a portfolio and comprehensive backend-learning project. The developer selected application-owned session authentication and PostgreSQL with TypeORM/Data Mapper, using maintained cryptographic primitives/libraries. Stack Auth is an inherited frontend-template dependency scheduled for later removal, not the target identity owner. Its removal and the replacement UI have not been implemented. Compare effective price/capability across suitable providers, including Cloudflare and alternatives such as Vercel/Supabase; Cloudflare is not a hosting restriction. Detailed session policies, package versions and hosting remain open; ADR 0001 records the accepted stack.
- Keep business rules independent of HTTP handlers, persistence details, storage providers, and payment/email SDKs. Separate request/response contracts from stored entities; introduce abstractions where they make an integration replaceable or a boundary testable.
- The frontend currently uses Stack Auth for sign-in, account management, and teams. The target backend owns local users, credentials, sessions, organizations, memberships and permissions. Design the transition separately; do not make provider-team synchronization a prerequisite for new domain behavior. Never trust a client-supplied tenant ID without checking membership and permissions.
- Global user identities and platform roles differ from tenant-owned memberships and tenant/project roles. A global identity must not grant access to every tenant.
- Root model references use UUIDs. Define local identity uniqueness, credential/session ownership and account-deletion behavior before implementation. If external identities are added later, do not assume provider IDs match domain UUIDs; define mapping and synchronization at that time.
- User identity, profile, session, authentication-factor, and verification/reset-token concepts are represented by `User`, `UserIdentity`, `UserProfile`, `UserSession`, `AuthFactor`, and `UserToken`. Implement the required outcomes with a minimal local model; reference classes are not a requirement to create every table now. Do not carry template-provider credentials into the new local store.
- The five `UserStatus` values remain `active`, `inactive`, `pending_verification`, `frozen`, and `deleted` in the root enum reference. Authentication factors and verification/reset/MFA token types are also preserved there. MFA is a later enhancement under the [canonical SRS release boundaries](TenantFlow-SRS.md#24-canonical-release-boundaries); model support is not an MVP implementation commitment.

## 2. Data integrity and lifecycle

The SRS sections 7-8 remain authoritative for tenant boundaries, UUIDs, foreign keys, explicit join tables, soft deletion, and retained history. Validate a tenant-owned child through its parent as well as its own identifiers. System-level records may have no tenant; this must be explicit rather than an unscoped query exception.

The following details appeared in tutorial mappings. Preserve them for design review, not as automatically approved constraints:

| Topic | Candidate retained for review | Decision required |
| --- | --- | --- |
| User identifiers | Required email and slug, unique indexes, candidate maximum 255 characters each. | Define email normalization and uniqueness scope consistently with the identity provider. Confirm slug generation and collision behavior. |
| Role/permission vocabulary | Required scope and name; candidate scope length 50, name length 255, description required. | Enforce system/tenant/project scope consistency with nullable tenant/project references and assignment boundaries. |
| Role joins | Unique `(role_id, permission_id)` and `(user_id, role_id)` pairs. | Add appropriate uniqueness for tenant/member/project assignment joins and prevent cross-scope assignments. |
| External identities | Candidate unique `(provider, provider_user_id)`; provider length 50, provider user ID length 255. Local credentials were modeled with a nullable provider. | Define local/provider identity uniqueness and null behavior explicitly; do not rely on a nullable unique index alone. |
| Sessions | Store a refresh-token hash when TenantFlow owns refresh tokens; active/expiry/revocation state, IP, user agent, device, and timestamps. Candidate lengths: IP 45, user agent 500, device 255. | Define expiry, revocation and rotation policy, retention, and provider ownership. Nullable expiry in a reference model is not approval for unbounded sessions. |
| Authentication factors | Type, display name (candidate length 255), enabled/primary flags, verification/last-used timestamps, and provider-specific metadata modeled as JSONB. | Protect secret metadata and decide which factors the identity provider manages. |
| User profiles | Optional first/last name (100 each), phone (20), location (255), bio (500), avatar URL (500); one profile per user. | Recheck lengths and one-to-one uniqueness against product/provider needs; these were example limits. |
| Verification/reset tokens | Hash, purpose, expiry, used/revoked timestamps. A tutorial proposed one unused/unrevoked token per user and purpose. | Decide whether that limit is needed and how expiry/reissue works. The old filtered-index example is not portable SQL and must not be reused as a migration. |
| UUIDs and enum storage | UUID primary keys and stable lifecycle strings. | Choose application/database UUID generation deliberately; never rely on retired language enum ordinals. |
| Timestamps | Creation/update/deletion timestamps and UTC semantics. | Decide timezone-aware storage and who updates `updated_at`; a default alone does not update it on writes. |
| Deletion | Tutorial examples cascaded profiles, identities, sessions, factors, tokens and role joins, and cleared an optional primary role reference. | Reconcile every foreign key with SRS historical-data rules. Do not cascade-delete audit/billing history or bypass soft-deletion and retention policy. |

The root model files remain design references, not migrations or runtime validators. Known naming issues include comments referring to `Project.id` and `UserMembership.id` where types are named `TenantProject` and `TenantMembership`. The combination of `User.role_id`, system-role assignments, and membership/project-role assignments needs one consistent authorization model. Resolve these before implementing persistence; they were not silently redesigned during cleanup.

## 3. API and security requirements

- Account lifecycle outcomes include registration, verification, sign-in/out, session renewal/revocation, password reset/change, and future MFA. TenantFlow owns the target lifecycle; choose opaque sessions versus access/refresh tokens and define cookie/CSRF or bearer handling before defining API routes. MFA remains future scope.
- Validate incoming data at the API boundary and enforce domain invariants in services and database constraints where practical. Keep validation, authentication, authorization, missing-record, and unexpected-failure outcomes distinguishable without disclosing sensitive internals.
- Return explicit response contracts. Never serialize password hashes, refresh-token hashes, verification/reset-token hashes, authentication secrets, or internal entity relationships directly to clients. Email/profile exposure must respect the caller's permissions.
- Use supported password/token handling from the chosen identity system or a reviewed library. Retired tutorial hashing parameters and custom token-service examples are not a security design to port.
- Use HTTPS for production traffic and avoid sensitive-data logging; local debugging instructions must not expose credentials or token contents.
- Enforce tenant isolation and permission checks for reads and writes, including nested resources, list/filter endpoints, assignment joins, and file access. UI visibility and frontend team selection do not enforce API authorization.
- Common lists need pagination/filtering and tenant-aware indexes. Preserve append-only audit records with actor, tenant, target, action and time; consider safe old/new-value metadata without logging credentials.
- Keep API contracts documented with OpenAPI and a discoverable exploration interface when implemented. The existing `/health-check` is liveness only; readiness and database connectivity checks remain future implementation work.
- Plan structured, redacted logs, correlation, diagnosable errors, optional tracing/metrics, rate limiting, and tests for tenant isolation, permissions, session lifecycle and integration boundaries. Libraries and endpoint paths remain undecided.

## 4. Integrations and operations

- PostgreSQL with TypeORM repositories/Data Mapper is selected; the existing PostgreSQL service remains the development baseline. D1 is no longer an active engine-selection task. Host processes use PostgreSQL's published local port; containers on the Compose network use the service hostname. Schema changes need reviewed TypeORM migrations and an explicit verification procedure once persistence exists. Preserve the current Compose data/volume configuration.
- Keep outbound integration clients bounded by timeouts and appropriate retry/circuit-breaking policies. Retry state-changing calls only with an idempotency strategy.
- Retain billing plans/limits, provider webhook verification and idempotency, append-only billing history, and test-mode payment integration. Stripe remains the planned provider in the SRS; never handle raw card data. No payment SDK is selected by this cleanup.
- Keep email verification/reset/invitation delivery requirements and optional later notification delivery. Notification preferences, read state, and tenant-aware records must work independently of any optional live-push transport.
- Store file metadata and ownership in the selected relational database; keep binaries behind a storage boundary, with local storage possible for development and object storage later. Cloudflare R2 is a later candidate, not configured storage. Preserve size/type validation and authorized download requirements.
- Plan lightweight background processing before durable scheduling. Notification delivery, retry behavior and webhook work must remain traceable and recoverable. Choose scheduling/queue tools only when needed.
- Keep caching optional: tenant-aware keys, appropriate invalidation, local in-memory lookups where useful, and a distributed cache only when justified. Redis, mail-testing services, durable workers, live-push transports and tracing infrastructure are not configured in this checkout.
- Use environment configuration with startup validation and managed deployment secrets when implemented. Database, identity, email, storage and billing settings need actual consumers before they become required variables. Separate environment credentials and never expose server secrets through browser-public variables or logs.

## 5. Decisions before implementation

1. Use the [canonical SRS release boundaries](TenantFlow-SRS.md#24-canonical-release-boundaries) and reconciled version plan as the scope baseline. Record any requested scope change explicitly; old dates, checkboxes and future model fields do not establish completed delivery or new commitments.
2. Retain the implemented Nest 12/Express, npm, ESM/NodeNext and Vitest/Vite foundation while evaluating deployment compatibility. Choose persistence/migrations and standardize supported runtime versions before new integration work.
3. Define local credential handling, session design, account lifecycle, organizations/memberships and permission ownership. Stack Auth removal is a later frontend transition, not a prerequisite for backend design.
4. Review the data-integrity candidates above and produce a consistent schema/ERD with tenant-aware constraints and retention rules.
5. Define the first API contracts, environment contract, startup commands, health checks, container/CI wiring and meaningful tests alongside the actual backend source.

### Current identity and database options

On 22 October 2026 the user confirmed session-based auth, PostgreSQL with an ORM, flexible provider selection and the first register/login/caller/logout slice. The table distinguishes that direction from proposed details. Use the [temporary auth development plan](../SESSION_AUTH_DEVELOPMENT_PLAN.md) for the active Step 1 worksheet; keep broader task order in the [roadmap](../planning/ROADMAP.md#current-priorities-and-learning-preferences).

On 23 October 2026 the developer accepted [ADR 0001](../architecture/decisions/0001-BACKEND-STACK-AND-SESSION-AUTH.md): TypeORM with Data Mapper/repositories, reviewed migrations, application-owned PostgreSQL sessions, Argon2id, existing Nest/Express validation/configuration/testing, Swagger, Helmet, throttling and built-in JSON logging. This supersedes ORM selection and the earlier Prisma/raw-driver starting recommendations. It does not establish installed dependencies, migrations or working auth; detailed policies and compatibility checks remain open.

| Choice | Proposed starting point | Tradeoff / acceptance evidence |
| --- | --- | --- |
| Authentication ownership | Application-owned email/password and account lifecycle, per user direction. Use reviewed password hashing, randomness and token/signature libraries. | More lifecycle, recovery, abuse prevention and testing work than managed identity; learning value is the reason for ownership. No custom cryptographic algorithms. |
| Session model | Application-owned opaque cookie sessions with only a digest persisted, implemented through a small service and Nest guard, are selected in ADR 0001. | Cookie topology, CSRF, expiry/renewal and revocation details remain Step 1 decisions. Passport/express-session and access JWT plus refresh tokens are not the initial architecture. |
| Main database | PostgreSQL through TypeORM is selected; keep the local service initially. | Released versions, migrations execution and hosting remain open. Hyperdrive would connect Workers to existing PostgreSQL, not host the database. |
| Cloudflare-native alternative | Workers plus D1 is retained as an evaluated alternative, not the selected engine/runtime. | SQLite and its platform constraints remain useful comparison context. Do not reopen engine selection without a new requirement or concrete blocker. |
| Data access | TypeORM, `@nestjs/typeorm` and `pg`, Data Mapper/repositories and TypeORM migrations with synchronization disabled are selected. | Validate released versions, entity mappings, ESM runtime/CLI behavior and transaction-bound repositories. No ORM integration is implemented yet. |
| Password hashing and hosting | Argon2id through a maintained implementation is selected; verify target-runtime support and benchmark settings. | Compare suitable hosts without a Cloudflare-only requirement. Do not reduce password protection to fit a quota. No hosted runtime/hashing compatibility has been locally verified. |

Before the first domain migration, finalize the PostgreSQL ORM/migration workflow, email normalization/uniqueness, session expiry/revocation/renewal, applicable tenant ownership, foreign keys and history retention. Design recovery/verification tokens with their consuming lifecycle flows. Check deployment compatibility before accepting a particular host; Cloudflare-native deployment is not a prerequisite. Keep the backend in `backend/`; do not replace NestJS merely because a tutorial uses another framework.
